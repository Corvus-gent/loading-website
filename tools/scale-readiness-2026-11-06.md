# Production recovery and scale audit — 6 November 2026

Production is restored, but this is **not a sign-off for 500 concurrent visitors**. The free production Redis remains the first capacity and durability risk. The separate paid database was used only by local test processes and was emptied afterwards: **DBSIZE 0**. No production/preview Redis settings were changed for the load test.

The one production configuration bug fixed during this audit was a missing CRON_SECRET. Both environments now have it; the existing restoration commit was redeployed to production. An authenticated snapshot job actually completed at **11:42:43 UTC**. The next scheduled snapshot run is **7 November, 02:12 UTC / 03:12 Brussels**; that future scheduled execution has not been observed. The X/SF backup cron is 03:17 UTC / 04:17 Brussels.

## Load-test evidence and limitations

All tests were CLI/Node driven. No production write endpoint was load-tested. Production had only bounded feature checks, with synthetic contributions cleaned up. Short-lived anti-abuse counters expire normally; an actual login audit record remains under its normal retention.

Preview: authenticated deployment bypass, read-only HTML, one bounded burst per level, no browser assets/API fan-out, no redirect following. Values below are **p50 / p95 ms**, followed by request errors. Higher levels stopped after the first error on that route.

- / — 200: 5,481 / 5,723, 0/200 errors; 500: 8,337 / 14,135, 0/500; 1,000: 12,178 / 23,376, 11/1,000 timeouts (1.1%).
- /realm/ — 200: 6,056 / 6,906, 0/200; 500: 14,864 / 23,918, 104/500 timeouts (20.8%). 1,000 not attempted after failures.
- /music/ — 200: 7,188 / 8,878, 0/200; 500: 11,473 / 25,608, 53/500 timeouts (10.6%). 1,000 not attempted.
- /games/ — 200: 4,487 / 7,653, 0/200; 500: 8,582 / 14,968, 1/500 timeout (0.2%). 1,000 not attempted.
- /links/gabe — 200: 4,077 / 5,300, 1/200 timeout (0.5%). Higher levels not attempted.
- Preview /stats/ returns 308 to the production stats hostname. It was **not followed or stress-tested**, to avoid silently moving the test into production.

These are local-generator-to-preview measurements, not Frankfurt-origin timings or an independently verified Belgium network. They include client/network/TLS constraints. They do not establish that Vercel itself hit a capacity limit. No HTTP error status was observed among completed preview responses; the failures were client timeouts. Do not use them to promise a production latency SLO.

API: actual route handlers on eight local Node workers against NEW only. The application's existing exact-host, dated plaintext exception was configured only in those processes. External health HTTP probes were replaced with fixtures, and external service credentials were absent, so the test did not amplify traffic into production/third parties. Redis calls, rate-limit writes, connection reuse, health aggregation and music state were real. Final API tests ran after the preview burst tests had ended; an earlier overlapping exploratory run was discarded as a capacity comparison.

- /api/music, 200 concurrent: 15,713 / 29,523 ms; 117 completed 200 responses, **83/200 timeouts (41.5%)** at 30 s. Stopped here; 500/1,000 would not be a responsible next step after failure. Peak memory 7.55 MB; peak clients 10. Recorded 1,820 Redis commands.
- /api/health, 200: 4,581 / 4,597 ms, 0/200 HTTP errors; 500: 4,626 / 4,665 ms, 0/500; 1,000: 4,668 / 4,711 ms, 0/1,000. Peak memory 8.20 MB; nine clients. Responses can still say degraded because optional dependencies were deliberately absent. **200 is not proof all checks were healthy.**
- No Redis connection rejection was observed; the highest observed client count was 10, not a demonstrated 256-connection ceiling. Music timed out before a higher request ramp. A health run hit the guard during exploratory testing, which was stopped; no unbounded saturation test was performed.
- Local sequential Redis PINGs to both OLD and NEW were about 0.9–2.2 s; actual production health measured Redis at 17 ms. Local API latency therefore cannot be attributed solely to the database or extrapolated to Vercel Frankfurt. Repeat from a nearby, independently instrumented runner after caching fixes.
- One normal music origin GET is nine helper-level Redis operations. The stored catalog is 53,323 bytes: at 100k music loads/day, fetching it afresh would transfer roughly **160 GB/month from Redis**, before other payloads. This is a worst-case music-route scenario, not an assertion every visitor opens music. It exceeds NEW’s standard 100 GB allowance and explains why caching matters even when RAM is mostly empty.
- Test cleanup: server processes stopped, destination host checked different from OLD, initial NEW DBSIZE confirmed zero, only test-generated prefixes allowed, then NEW-only FLUSHDB; verified **DBSIZE 0** afterwards. Production/preview Redis environment variables were not switched.

## Integrity boundaries

There is no pre-outage key/TTL manifest. The available baseline was taken **6 Nov 11:04 UTC, during the outage before restoration**: 57 keys, 258 tracks, five music votes, catalog/vote hashes. Thus “all TTLs unchanged since before the outage” is unprovable. Expiring records also correctly disappear while time passes.

Read-only prefix snapshot at 11:17 UTC: health 19, stats 27, music 8, game 18, cv 8, games 6, cli 4, voted 6, sess 1, logins 1, lang_votes 1 (99 keys; 48 persistent, 51 expiring). A 12:03 snapshot during audit had 115 keys, including refreshed snapshots, health records and temporary audit limits: music 11, stats 32, health 19, sf 1, cv 8, game 18, games 8, cli 5, voted 7, privacy 2, sess 1, otp 1, logins 1, lang_votes 1. Empty counters created by the synthetic guess/curl test were subsequently removed conditionally only while still zero. Counts are not evidence of data loss or duplicates by themselves.

## First three fixes before promoting the site

1. **P0 — finish TLS on the existing paid Redis Cloud Frankfurt database and migrate with durability.** Keep the $10 plan already bought; verify AOF/backup configuration, pin existing signing secrets, copy keys with remaining TTLs, verify hashes/counts and only then switch. Remove the temporary plaintext exception afterwards. Keep OLD seven stable days. A larger tier is conditional on the cached workload, not a substitute for caching.
2. **P0 — remove anonymous Redis writes from public reads and cache the catalog/counts/health status.** Dedicated interaction endpoints mint challenges/voter state; a protected sampler writes health; public GETs read snapshots from CDN. Add bounded dependency timeouts and global backpressure. Then re-run from Frankfurt with separate load generators and real Vercel instance/concurrency telemetry.
3. **P1 — make failures visible and bounded.** Install and test the external five-minute monitor, verify the next cron execution, fix stale-snapshot false alarms, add quota/spend/memory/connection alerts, and apply the reviewed retention migration. Retain last-good public snapshots through a Redis outage.
