02 · why it's an evaluation problem

The page doesn't know it's being benchmarked. It doesn't have to.

Recognising an automated visitor is enough. Your detector scores an observation, and the attacker gets a say in what that observation is.

  • Two systems, two exposures.The discovery agent searched repo code (exfiltration to Telegram, Discord and form services, brand-named repos). On Spaces that source is public, so visitor cloaking barely touches it. A detonator that renders the link and judges a screenshot, which is how Noon is described, is exactly what this trick aims at.
  • Your test set inherits the blind spot.If labelled examples come from pages you could see, the pages that hid well are under-represented. The benchmark looks better for the wrong reason.
  • 42 is a count, not a recall.The search was scoped by exfiltration pattern and every hit was checked by hand, so the finds are solid. The misses are unmeasured, and the write-up says so itself. That honesty is a big part of why I wanted to write this.
03 · what I'd run first

A benchmark that changes who's looking, not just what's there. planned · not run yet

Small, local and defensive. The question: how much does a detector's score depend on the observation conditions, and does a cheap source-level check catch what rendering misses?

  1. Screenshot-based detection drops measurably on pages that serve automated visitors something else. A source-level baseline drops much less.
  2. A test set built only from pages a scanner could render overstates detection, compared with one where the hiding is known by construction.
  3. Combining both views beats either one alone, but less than you'd hope. The gap is the interesting number.
pagesSynthetic, fictional brands, forms that post dummy data to localhost. A known fraction behave differently for automated visitors, so ground truth is fixed by construction.
conditionsThe same set seen as: plain HTTP fetch · headless browser · full browser profile · source only.
detectorsA vision-model screenshot judge, and a simple static-source rule baseline with no agent.
reportDetection rate per condition with bootstrap intervals. The headline is the gap between conditions, not the best score. Plus failure cases: what the detector saw next to what a person saw.
wrong ifScores barely move across conditions. Then the hiding doesn't matter for this class of detector, and I'll say so.
limitsNo live sites, no real brands, no credential collection, no evasion techniques published. Code and data public once it runs, including the parts that didn't work.

If this turns out to be obvious on your side, I'd much rather hear which part is actually hard.
